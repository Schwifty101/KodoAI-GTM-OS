## Commands
- `uv run pytest -q` runs the suite. Tests marked `db` hit the real Supabase project and clean up after themselves.
- `uv run python -m gtm.cli <pass>` runs a pass: scrape, clean, enrich, signals, select, draft, followups, send, replies. Sending rules: see Sending below.
  - `enqueue <kind> -- <flags>` queues a pass as a job; `worker [--poll 15]` runs queued jobs (plus `check-drafts`, `redraft`) and the send tick on its own thread.
  - `sheet-format [--confirm] [--tab T]` (CLI only) normalises sheet colours, headers and conditional rules; dry run by default, verifies marks after writing. Standard: `docs/SHEET-GUIDELINES.md`. `--sheet-id ID` (import-sheet, sheet-format, sheet-queue, sheet-paint) rehearses on a copy without saving it; `import-sheet --confirm --sheet-id COPY` still writes real leads, so rehearse that as a dry run only.
  - Sheet passes (read `sheet_id` from Settings; dry run unless `--confirm`; also worker job kinds): `import-sheet [--tab T]`, `verify-sheet --batch ID [--limit N]` (0.5 Hunter credit per email, bucket `hunter_import`, refuses without `--confirm`), `sheet-queue` (daily on the worker when `sheet_queue_on`), `sheet-paint` (needs `sheet_writeback_on`; `sheet_queue_on` gates only the daily schedule, not a manual `enqueue sheet-queue --confirm`). Migration 0015 is applied. `sheet-paint` also writes the OS-owned `os_status` column (sent/dropped/open) and runs daily on the worker after the queue when `sheet_writeback_on` (Plan 7, deployed 2026-11-24). The first colour paint, the first Queue-tab write, the `sheets-token` secret and the VM deploy are still hard gates: see `docs/runbooks/cloud-runner.md`. Order for a sheet batch: `import-sheet --confirm`, `clean`, `verify-sheet --confirm` (before enrich), `enrich`, `signals`, `select`.
  - `mailbox add|unpause`; `import-history FILE` (Notion history into suppression).
  - `walk [--tiles N]` scrapes and cleans the next uncovered tiles of the coverage table; `seed-coverage` fills it from `gtm/data/metros.csv`; `tz-backfill` sets `leads.tz` (free). `select` numbers batches of 100.
  - `send` is a dry run unless `--confirm`.
  - If the Gmail token is rejected, delete `.secrets/token_<mailbox>.json` and rerun on the Mac to re-auth.
  - `enrich` flags: `--limit`; `--named-only` (with `--retry-no-buyer`: only `no_buyer` leads whose owner is named; `cleaned` leads are still processed); `--finders` (default `site,search,research,prospeo`; `hunter` and `harvest` opt-in); `--harvest-budget`; `--research-budget`; `--retry-no-buyer` (spends credits again; also processes cleaned leads).
- Autopilot (`gtm/autopilot.py`, worker tick every loop, card on `/batches`): when `autopilot_on`, it queues the existing passes one at a time (clean, verify-sheet, enrich, signals, select, draft, walk) until the current batch of 100 is full, never approves or sends. `autopilot_limit_usd` (0 = no limit) is a soft run limit counted from `autopilot_started_at` (Start or Resume resets it); daily caps still apply. A daily cap retries next UTC day, credit out pauses until Resume. `batch_base` ({"3": 32}) counts leads already in a batch outside the OS (Notion Batch03); `renumber-batch --from N --to M [--confirm]` moves selected leads (dry run by default). Rehearse with `uv run python scripts/rehearse_autopilot.py` (TEST_AP_ rows only).
- Yield-aware walk: `walk_yield_order` (default on) makes `claim_tiles` prefer tiles in states with the best smoothed enriched rate (state rate from ALL leads, every third claim explores an unsampled state); `clean_category_strict` (default on) rejects name-only med spas as `low_yield_category`. Both off = old behaviour. `uv run python -m scripts.yield_report` prints yield per state, per scrape run and enriched per dollar by day. Email-finder pilot (Icypeas vs Anymail, 20 leads): `scripts/email_pilot.py sample|run --arm ...|score`; `run` and `score` spend credits, owner's yes first; keys `ICYPEAS_API_KEY`, `ANYMAIL_API_KEY` in `.env`.
- UI run-now (Plan 8): Settings Sheet block, /batches intake row, /drafts "Draft an outreach batch" (`draft --batch-no N`, cross-source batch of 100) and /send "Draft follow-ups" enqueue jobs through `web/lib/actions.ts`. Sheet passes use Preview (job without `--confirm`) then Apply (`enqueueApply`: needs a `done` preview with the same argv under 24 h old); `enqueueGuarded` blocks a hand-typed `--confirm` for import-sheet, verify-sheet, sheet-queue and sheet-paint. clean, signals, select, draft and followups have no dry run, so they get a confirm dialog. Pure logic: `web/lib/runnow.ts`; check: `web/scripts/runnow_unit.mts`, `verify_runnow.mts`.
- Recontact (Plan 9, built, OFF by default; migration 0018 is written, NOT applied: owner gate): `backfill-contacts FILE [--sheet] [--confirm]` fills the `contact_history` ledger from the Notion export (FILE; `--sheet` adds the sheet-sent rows) and `recontact [--limit N] [--confirm]` (also a worker kind and a Settings Preview/Apply block) creates round + 1 leads for released contacts. Both are dry runs unless `--confirm`; tests and agents never run either with `--confirm` on the real database. `PYTHONPATH=. uv run python scripts/recontact_parity.py` (read-only, counts only) asserts the flag-off blocklists equal the pre-Plan-9 ones and prints what the flag would release. Gates in order: `docs/runbooks/cloud-runner.md`, Recontact.
- `bash deploy/deploy.sh gtm-worker us-west1-b` deploys committed HEAD to the VM; the worker runs there under systemd (runbook: `docs/runbooks/cloud-runner.md`). Deploy only when the queue is idle.
- `cd web && npm run dev` runs the UI locally (login: email link to the operator address). The UI has a Drafts page (sample-first review, edit in place, approve in bulk, regenerate a batch with an instruction) and a Send page (Today and Follow-ups tabs, Start sending, Pause). Edit drafts in the OS: the database text is what goes out.
- `cd web && node --env-file=.env.local --env-file=../.env --import tsx scripts/verify.mts` checks the UI's write actions against the real database under RLS; `verify_scrape.mts` and `verify_batches.mts` (same invocation) check the `/scrape` and `/batches` pages' queries and writes. `uv run python scripts/verify_tiles.py` checks coverage tile names with the Geocoding API. The UI also has `/scrape` (coverage, Run N tiles now, retry failed tiles) and `/batches` (batch status, Retry later for named no_buyer leads).

## Sending (single source)
- Drafts live in the database (`touches` statuses: drafted, held, edited, approved, scheduled, sending, sent, cancelled). The Gmail draft is created only at send time; the database text is what goes out.
- `send_tick` (`gtm/send.py`) on the worker is the one sender: it runs every 60 s while the `sending_on` setting is on (Start sending / Pause on the Send page). Terminal `send --confirm` forces one tick (sends what is due now; only `--confirm` reads replies first).
- Window: Mon-Fri 9:00-16:00 in the lead's local time (null tz = America/Chicago).
- `send_anytime` setting and `send --confirm --anytime` skip the window: REHEARSAL ONLY, keep off.
- Ramp: 20 on the first real sending day, +3 per sending day, cap 40 per mailbox; restart from 20 after an auto-pause (`mailbox unpause` sets ramp_from). The tick stamps today's allowance on the mailbox (`allowance_today`, `allowance_date`) and the Send page shows that stamp; there is no second formula.
- Auto-pause at 3% bounce over 20 sends (7-day window).
- Replies are read at most every 10 minutes per mailbox. A Gmail token or auth failure pauses that mailbox with a reason.
- Gmail runs on the Mac (interactive OAuth) and on the VM (token from Secret Manager; a headless worker never opens a browser).
- Rehearsal and manual test rows use the prefix `REHEARSAL_` (never `TEST_`: db tests delete every `TEST_%` lead). Run one pytest process at a time (`mkdir /tmp/gtm-pytest.lock`). A session fixture sweeps empty test-named batches left by `new_batch`; reply and send tests use a fixture mailbox, never the real one.
- Recontact rule (Plan 9, spec `docs/superpowers/specs/2026-11-26-recontact-policy-design.md`, section 12 wins): setting `recontact_on` is off by default and with it off `select` reads blocklists exactly as before (the ledger is not queried). On, only suppression rows with reason exactly `notion-contacted` or `sheet-sent` can be lifted, and only by a clear ledger row: outcome `no_reply` or `auto_reply`, last send `recontact_days` (60) or more ago, round below `recontact_max_rounds` (3). Never recontacted: bounce, opt-out, not-interested, `do-not-contact`, `sheet-dropped`, any reply, booked, client, disqualified, an unknown reason, any row with missing or unparseable evidence. A released contact gets a NEW lead per round (`place_id` `recontact:<ledger id>`, `round` + 1, `history_id`); old lead, touches and suppression rows are never edited. Re-verification spends Hunter from bucket `hunter_recontact` (`recontact_hunter_allowance_credits`, default 0 = cannot spend). The pass never approves or sends and autopilot has no recontact stage; the new lead then goes through signals, select, Review, Draft and Send like any other.

## Rules
- Supabase Postgres is the only database. `gtm/config.py` is the only reader of the environment.
- Statuses: scraped, cleaned/rejected, enriched/no_buyer, signalled, selected, drafted, sent, replied, booked; side states bounced, suppressed, unsubscribed.
- US only. No day spas. Lead identity is Google place ID, unique globally.
- A signal needs a source URL and a date. Never invent one.
- Enriched means a named decision-maker (founder, owner, CEO or equivalent) with a verified email. Role addresses never qualify. The email must have verification `valid` and score >= 75 (`accept_all` fails). Failed leads stay `no_buyer` but keep a saved name for retries.
- LLM: Vertex Gemini primary, Groq fallback (`gtm/llm.py`); replies use `gemini-3.1-flash-lite` (`complete_reply_json`, `gemini_lite_*` prices, unverified). Owner-finding measurements: `docs/spikes/owner_routes.md`.
- Check `suppression` and "already contacted" before every draft and send. A reply or bounce stops that lead's remaining touches. A bare decline reply ("not interested") is suppressed with reason `not-interested`; a wrongly suppressed lead is fixed in the database. Cadence is Day 0/3/7, no Touch 4.
- Footer values (`POSTAL_ADDRESS`, `AD_DISCLOSURE`, `OPT_OUT_LINE`) are empty by default: append if set, never invent, never block sending on empty.
- Every paid call writes a `cost_log` row. Never print or commit keys. The Supabase secret key is script-side only, never in the browser.
- Send is always a separate explicit action from draft.
