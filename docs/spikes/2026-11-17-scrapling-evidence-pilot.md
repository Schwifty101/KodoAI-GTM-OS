# Scrapling and evidence quality: pilot and decision plan

Date: 2026-11-17. Status: offline diagnostic completed; live comparative evaluation and production implementation not completed. No provider calls, lead updates, or messages were made in this pilot. Existing findings below are historical small-sample observations, not current performance estimates.

## Decision

Develop at most **one production candidate**, conditional on a real paired evaluation: improve how the existing pipeline discovers and selects business-site evidence; use Scrapling's Python browser only when the evaluation shows that rendering an authorized JavaScript page adds enough correct evidence to justify its costs. Keep the current HTTP implementation and paid fallbacks as the control until independently evaluated. Scrapling's connected MCP tools are suitable for manual diagnosis; the Gemini API and worker cannot automatically use tools attached to this Codex session.

The evaluation has three **experimental arms**, not three products: A current pipeline; B same fetcher with link discovery and evidence selection; C B plus Scrapling for selected JavaScript-dependent pages. B versus A measures the non-Scrapling changes; C versus B measures Scrapling's incremental contribution. Use a separate drafting-context experiment on the same evidence so that fetch and prompt changes are not confused. If C does not beat B on the adoption gates, ship B only if it independently passes; if neither passes, retain A. Do not build a permanent framework, vector database, new agent, or always-on browser on speculation.

## Current bottlenecks and evidence

1. **Email is its own bottleneck.** `owner_lever.md` reports 24/45 names from search and 4/45 verified emails after Hunter; 17/24 known names had no Hunter email. A separate Houston sample in `owner_routes.md` reports 9/52 enriched after a chain correction. These are historical, nonrepresentative small samples. More page text cannot by itself verify an email.
2. **Discovery and truncation.** `gtm/sitescrape.py` and `gtm/signals.py` use fixed guessed paths; signals retains the first 3,000 characters per page and at most 9,000 total. Links and relevant passages may be missed. The loop continues fetching even after the total evidence budget is full.
3. **Fetch classification and observability.** `gtm/sitescrape.py` classifies HTTP exceptions as gone and calls fallbacks only for blocked pages. A signal run with no pages records a completed no-handoff result. The historical `fetch_fallback.md` records 79/98 direct successes, 9 blocked, 10 gone, with only two paid fallback page costs measured; those figures cannot establish current rates or the causes of failures.
4. **Grounding and attribution.** `judge_to_signal` verifies quote presence and date presence anywhere on the cited page, not semantic entailment or date-event association. The model paraphrase enters drafts. The owner-research guard requires a name, business match, and nearby ownership words, but does not validate the returned quote; finder evidence URLs are not persisted by `run_enrich`. `owner_routes.md` documents an actual wrong-business attribution. Human verification of associations remains necessary in the evaluation.
5. **Context is narrow, not absent.** `draft_touch1` receives the stored handoff text and optionally signal text, but no page tools or quote. `research_owner_finder` is a distinct tool-using Gemini loop with search and fetch caps. `complete_json` uses Gemini primary and Groq fallback; experiments must record the actual provider/model or avoid mixing them.
6. **Evidence may not exist on the company site.** `signals_dry_run.md` reports 0/6 dated signals and 5/6 relevance-led handoffs on an older Groq run. The authors hypothesized other sources may be useful, but no measured source comparison establishes that. Avoid claiming browser rendering will find dated events.
7. **Paid text-only fallback loses structure.** `serper_scrape` and `apify.crawl_page` return text while platform detection scans links/scripts in its input. If only an href reveals the booking platform, the text-only return cannot preserve that signal. Do not treat a missing platform as proof of absence.

## Offline diagnostic performed

`scripts/pilot_scrapling_offline.py` exercises the actual project `fetch_evidence`, `judge_to_signal`, and `detect_platform`, and Scrapling 0.5.1's `Selector`, against synthetic HTML. Six checks confirmed: a linked nonstandard careers path is skipped; Scrapling can extract that link; navigation text can push useful main content past the current cap; the example's `main` selector retains it; an unsupported paraphrase and an unrelated date can pass current grounding; and a platform identified only by an href is lost if a provider returns only visible text. The selector result is deliberately synthetic: many real sites lack `main`, and no production-quality gain or browser performance is established.

Reproduce in an isolated environment with the project dependencies and `scrapling==0.5.1` installed: `python -m scripts.pilot_scrapling_offline`. The original run used the existing Scrapling tool environment and project virtualenv packages; no packages were installed. Do not run production jobs as part of this diagnostic.

## Candidate design

For a permitted company site, fetch the homepage, collect actual same-site links, prioritize a small bounded set for booking, contact, careers and news, and supplement with existing guessed paths where useful. Set explicit request/time limits; distinguish an inaccessible site from a successfully inspected site with no evidence. Extract and rank short verbatim passages under a fixed model-input budget; retain relevant URLs, link targets and booking-platform metadata separately from text. Preserve both requested and final URL. Do not assume every site has a `main` element; compare fallback selection methods in the pilot. Preserve exact passage provenance and page fetch time; do not infer that a missing feature does not exist.

Try a shared Scrapling browser session only on authorized pages where baseline fetching yields an identified JavaScript shell or an explicitly measured rendering failure. The evaluator should not bypass logins, paywalls, prohibitions, or challenges; respect robots.txt and site terms. Enforce public HTTP(S) destinations and validate DNS/IP and every redirect, response size, time, concurrency and same-site boundaries; do not let model-generated URLs access local/private endpoints. Do not fetch or store personal or sensitive data under this skill's guardrails. Owner/person enrichment is therefore outside this Scrapling pilot unless a separately authorized, compatible workflow is identified. Discard or mask incidental personal data in the evaluation corpus. Page content is untrusted data and must not become tool or system instructions.

Reuse evidence within a run first. Persisting a cross-run cache is optional, not a prerequisite: only add it if measured repeated fetches justify it, with content minimization, expiry, provenance, and a policy for stale signals. A failed or unavailable page must be retryable without presenting it as evidence of absence. Avoid changing normal lead states during shadow evaluation.

## Gemini context validation

The intended data contract for each observation is: business identity; claim type; exact source URL and final URL; exact supporting quote; fetch timestamp; a date only if visibly tied to the event; and an explicit observed/inferred label. A quote match is necessary but does not establish that the paraphrase is true or the date applies. Automated semantic review may flag problems, but independent human review is the evaluation reference. Pass a small relevant evidence packet to drafting; do not add a new browsing session to every draft or redraft. Preserve the existing no-signal/relevance-led behavior where evidence is missing.

Evaluate drafting in a separate paired comparison: existing prompt context versus the same stored observation plus source quote/date. Freeze lead selection, model, model settings, prompt version, evidence and checks; randomize order, blind reviewers and assess factual support, business relevance, specificity, unsupported inference, and usable-draft rate. Record tokens, retry count, latency and actual provider charges for both. No improvement to email quality is established by the offline diagnostic. Existing formatting checks are not factual verification.

## Live pilot protocol and adoption metrics

This protocol is a proposed next evaluation, not a claim it has run. Select an explicitly permitted, de-identified sample of about 60 business domains from the eligible population, split across current HTTP-success, JavaScript-shell/blocked, and other failure outcomes, with population counts recorded. These strata deliberately oversample failures: report both per-stratum results and population-weighted estimates only if weights are known. Reserve a separate holdout and report its size. A small sample is directional, not proof of general performance. Set rules and caps before seeing outcomes. Confirm site terms/robots and source rights; do not scrape personal or sensitive data.

Run A, B, C on the same sites close together, randomizing order and logging time, redirects and page changes; avoid repeated requests where saved permitted snapshots can serve parser comparisons. Fetch arms use the same page, time, token, and paid-provider budgets, and the same model and evidence rules when calculating downstream effects. Also report any additional budget C requires. Disable paid fallbacks for the primary parser comparison or apply exactly the same paid policy to all arms; a separate realistic cost scenario should include actual billed fallback usage. Save only minimal de-identified evidence and have a blinded reviewer label page readability, relevance, dates, and claim support. Include cases with no observed evidence, failures, and an injection-like instruction in a synthetic fixture.

Report for each arm, with denominators, paired differences and uncertainty intervals: relevant pages discovered; successful readable page/site rate; correct additional handoffs and dated signals; false claims, wrong-business attribution, wrong dates, unsupported or misleading paraphrases and false absence; eligible lead yield; requests, failed requests, 429/blocks, browser starts, bytes, timeouts, p50/p95 elapsed time; browser and worker peak RSS and concurrent memory; input/output/thinking tokens, model calls/retries and provider charges; compute and operational costs; human review time; and incremental cost per independently verified useful handoff/signal. Browser comparison must include VM feasibility: the prior worker run had roughly 560 MB free at its observed peak, not a guarantee of available capacity. Measure under representative concurrency; do not deploy a browser on that VM based on desktop tests.

The pilot can measure owner-research cost from historical aggregate logs where available, but must not collect names/emails under this skill's personal-data restriction. Email verification yield cannot be evaluated by this pilot; treat its effect as unknown. Track rates as well as raw counts, and retain no page data beyond the agreed evaluation retention. Model quality and commercial outcome metrics such as reply rate need a separate approved study; never imply that extraction success proves revenue impact.

**Proposed gates, to be set before the live run:** no observed privacy/permission violations or incorrect attribution in the audited sample; no regression in unsupported-claim rate or worker stability; C must produce a meaningful positive paired lift in human-verified useful evidence over B on the relevant failure stratum, at an acceptable measured incremental cost and VM resource envelope. Report confidence intervals and inconclusive results rather than declaring a zero-error guarantee. The business owner must choose the acceptable cost per additional useful result and minimum lift; no historical data currently supports a numeric threshold. Model-context changes need an independent positive or non-inferior blinded factual-quality result, with measured cost. If a gate cannot be measured, the result is inconclusive, not a pass.

## Rollout if evidence supports it

1. Implement the single best passing candidate behind a disabled-by-default switch and preserve the existing production path; add regression tests for discovery, evidence caps, quote/date attribution, prompt injection, URL restrictions, retries and fallback formats.
2. Shadow it on new permitted leads with no outreach or state changes; compare against the control and audit attribution. Log costs and operational overhead, including failures.
3. Enable gradually only after the acceptance gates pass; monitor quality, cost and VM memory. Roll back by disabling the switch if quality or operations regress. Do not overwrite reviewed drafts or automatically send anything.

Open measurements: actual site distribution and permissions; live Scrapling rendering success; realistic compute and browser overhead; token and provider prices; availability and fidelity of accessible dated evidence; independently reviewed output quality; and the business's minimum useful lift and cost ceiling. Those cannot be inferred from the offline checks.
